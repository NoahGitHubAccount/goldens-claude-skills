# 依輸入類型抽取業務情境

整合測試案例可從多種素材長出來。共通目標：**找出「誰、為了什麼業務目的、跨哪些畫面/角色、讓什麼狀態改變」**。下表給各類素材的抽取著力點與陷阱。

多份素材並存時的優先序：
- **情境邊界**（哪些算一條情境、顆粒度）→ 以 **需求/SA 文件** 為準。
- **步驟細節**（按鈕名、欄位、導航路徑）→ 以 **操作手冊/截圖/程式碼** 補。
- **狀態與交接** → 綜合各素材的狀態詞與權限角色推得。

---

## 1. 系統分析文件（SA / 需求規格）
- **抽什麼**：用例（Use Case）、功能清單、角色權限矩陣、狀態圖、需求編號。
- **著力點**：用例本身常就是一條情境；角色權限矩陣直接給「使用角色」；狀態圖直接給狀態流轉鏈。
- **追溯**：需求編號直接帶入「對應需求編號」欄。
- **陷阱**：SA 常以「功能」為單位，需重組為「端到端流程」——一條情境可能橫跨多個功能。

## 2. 需求情境描述（User Story / 情境敘述）
- **抽什麼**：角色、目的、預期結果（「身為 X，我要 Y，以便 Z」）。
- **著力點**：天然就是情境；Z（目的）幫你判斷端到端的終點與結果檢視。
- **陷阱**：常缺中間操作步驟與導航，需配手冊/截圖補；缺則標 `（待補）`。

## 3. 功能畫面截圖
- **抽什麼**：選單路徑、頁籤、按鈕文字、表單欄位、列表欄位、狀態標籤。
- **著力點**：按鈕與狀態標籤 → 動作—結果配對；列表欄位 → 欄位驗證清單；選單 → 麵包屑導航。
- **陷阱**：截圖只給「畫面」不給「流程順序」；需靠狀態標籤與按鈕語意推斷流轉方向，並回問使用者確認。

## 4. 操作手冊 / SOP
- **抽什麼**：步驟序列、前置條件、注意事項、角色。
- **著力點**：手冊步驟最接近「驗測情境步驟」，常可近乎直譯；前置條件 → 前置準備段；注意事項 → 結果檢視或反例情境。
- **陷阱**：手冊是「教學口吻」含大量說明文字，需萃取為動作—結果配對；手冊常不寫追溯編號。

## 5. 程式碼（後端 API / 前端 view）
- **抽什麼**：路由與端點（畫面/功能對應）、狀態欄位與其 enum、權限檢查（角色）、狀態轉移邏輯（哪個 API 把 A 狀態變 B）。
- **著力點**：狀態 enum 與轉移邏輯 → 精確的狀態流轉鏈；權限中介層 → 使用角色與反例情境（權限不足）。
- **陷阱**：黑箱整合測試**不應引入前端內部型別/元件名**；只取對外可觀察的業務語意（畫面、按鈕、狀態名），技術細節留作佐證不入案例文字。

## 6. 單元測試案例
- **抽什麼**：被測函式對應的業務行為、邊界條件、狀態前後置（arrange/act/assert）。
- **著力點**：unit test 的 assert 提示「可觀察結果」；多個相關 unit test 串起來常拼出一條端到端情境。
- **「把單元測試補成整合測試」**：unit 驗單點正確；integration 要把這些單點**用真實業務流程串起來、跨角色跨畫面**驗證資料流轉。把多個 unit 的 act 串成一條使用者旅程，把它們的 assert 收斂成沿途的狀態斷言與最終結果檢視。
- **陷阱**：勿把 unit test 一對一翻成 integration case——那只是換皮，未達整合價值；必跨界。

---

## 抽取後的交付節奏
1. 先輸出「候選情境清單」（情境名稱＋角色＋一句目的），標出來源素材。
2. 與使用者確認顆粒度與取捨。
3. 再逐條展開三段式步驟。
4. 缺口一律標 `（待補，需確認）`，不臆造。
