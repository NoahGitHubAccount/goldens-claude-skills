# 整合測試案例撰寫（情境式）

把任何形式的素材轉成「情境式整合測試案例」。整合測試的價值在於驗證**一件業務從頭走到尾、跨畫面、跨角色、狀態正確流轉**——而不是單一畫面、單一按鈕的點擊。

## 四大核心觀念（每個案例都必須體現）

1. **情境端到端（End-to-end scenario）**：測的是一個完整業務流程，會橫跨多個畫面或步驟，不是孤立的單一操作。
2. **角色驅動（Role-driven）**：先綁定「誰在做」。整合的精髓在**跨角色交接**——A 角色送出 →（換角色）B 角色收到並接續。資料在角色之間流動，才是「整合」。
3. **狀態流轉（State transition）**：業務物件有狀態機（如 `待揀貨 → 已揀貨 → 待出貨 → 已出貨 → 已簽收`）。每一步操作都要伴隨一個**可觀察的狀態變化**，這就是驗證點。
4. **需求追溯（Traceability）**：每個情境掛一個（或多個）需求編號，確保「需求 ↔ 測試」雙向不漏項。若素材沒有編號，標 `（待補）` 而非留空。

## 產出格式（測試案例表）

預設輸出為 Markdown 表格，欄位固定：

| 情境名稱 | 使用角色 | 步驟（前置/驗測/結果） | 進度 | 對應需求編號 |
|---|---|---|---|---|

- **情境名稱**：用業務語言，不用技術語言。命名樣式：「如何<動作>」或「<業務>作業/流程/說明」。
- **使用角色**：一情境可掛多個角色（跨角色協作時全部列出）。
- **步驟**：採三段式（見下）。這是整份案例的核心。
- **進度**：`已完成 / 製作中 / 待撰寫`——標記撰寫狀態（非執行結果）。
- **對應需求編號**：如 `REQ-01-01`；無來源時標 `（待補）`。

> 若使用者要求 Excel／pytest／Gherkin 等其他輸出，先用本格式產出情境，再轉換——情境內容不變，只換載體。
> 要把案例落地為**可執行自動化測試**並產**測試報告（md→docx）**時，見 `references/automation-and-reporting.md`：原則是對齊專案既有單元測試架構與工具（page object / fixtures / marker / 報告器），不另立一套。

## 三段式步驟結構（步驟欄的寫法）

每個情境的步驟欄都依序包含三段：

1. **前置準備**：建立角色、權限、前置資料（例：「以具系統管理權限的帳號登入系統」「人事介接已同步該人員」）。沒有前置就跑不起來的整合測試會假綠。
2. **驗測情境步驟**：編號操作流程（1. 2. 3.）。撰寫技巧：
   - **導航路徑用麵包屑寫死**：`【訂單管理】>【出貨作業】>【揀貨單】`，人/機都能精確定位入口。
   - **操作動詞 ＋ 預期結果配對**：每個動作緊接一個可觀察結果（「點選[送出]」→「資料狀態變為『待出貨』」）。
   - **分支用子編號**：5.1 / 5.2 表示同一步的不同路徑。
   - **跨角色交接寫明換手**：「（換 B 角色登入）B 角色在【X 列表】看到此筆資料」。
3. **結果檢視**：最終斷言，明確可驗證（「返回列表，確認新建單位顯示於列表中」「狀態更新為『已封存』，此時不可修改或刪除」）。

完整格式規範與黃金範例見 `references/format-and-examples.md`。

## 工作流

### Step 1：辨識輸入類型，抽取候選情境
依素材類型用不同策略抽「業務情境」。對照表見 `references/extraction-by-input-type.md`。
- 多份素材並存時，以**需求/SA 文件**定情境邊界，以**手冊/截圖/程式碼**補步驟細節。
- 抽完先列「候選情境清單」（只列情境名稱＋角色），與使用者確認顆粒度後再展開步驟——避免方向錯了才發現。

### Step 2：逐情境展開三段式步驟
- 先標出該情境的**狀態流轉鏈**與**角色交接點**，步驟自然沿著狀態變化長出來。
- 每步驟動作都要能對應一個可觀察結果；找不到結果的步驟，多半是流程沒走完或顆粒太細。

### Step 3：掛需求追溯 + 品質檢核
逐案例過下方檢核表，未過的補齊。

### Step 4（選用）：自動化落地與報告
使用者要求產出可執行測試或報告時，依 `references/automation-and-reporting.md`：先盤點專案既有架構（pytest / page object / fixtures / marker / 報告器），讓整合測試沿用同一套；案例每元素對應 pytest 結構；報告先產 md 再轉 docx。

## 品質檢核表（每個案例逐項過）

- [ ] **跨界**：是否跨畫面或跨角色？（純單畫面操作 → 不是整合測試，應降級或合併）
- [ ] **前置**：開頭是否建立角色／權限／前置資料？
- [ ] **狀態**：每個關鍵步驟是否有可觀察的狀態／資料變化？
- [ ] **交接**：跨角色處是否寫明「換誰登入、在哪個畫面看到」？
- [ ] **斷言**：結尾是否有明確的結果檢視（可驗真假）？
- [ ] **追溯**：是否掛需求編號（或標『待補』）？
- [ ] **業務語言**：情境名稱與步驟是否用業務詞彙，而非內部技術型別／元件名？

## 邊界與原則

- **不發明需求**：素材沒寫的流程不臆造；缺口標 `（待補，需確認）` 交還使用者。
- **顆粒度**：一情境 = 一條可獨立驗證的業務價值線；過長就拆，過碎就併。
- **反例情境（選用）**：若使用者要求涵蓋異常流，另開情境（如「<X>__權限不足拒絕」），同樣走三段式，結果檢視驗「被正確阻擋」。
